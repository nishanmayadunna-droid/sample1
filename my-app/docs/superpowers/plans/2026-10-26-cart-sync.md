# Cart Sync to Account Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Save a signed-in shopper's cart to their account and restore it on any device, merging a guest cart on sign-in and clearing the browser cart on sign-out.

**Architecture:** The localStorage cart store stays the UI's source of truth. A render-less `CartSync` client component decides (via pure `decideSync`) whether to merge, pull, clear or do nothing, and a small debounced saver pushes the whole cart to a `public.carts` row through Server Actions that take the user id from `auth()` only.

**Tech Stack:** Next.js 16.2.12, React 19.2, Auth.js v5 (`next-auth/react` `useSession`), Supabase (secret-key client), Vitest 4.

**Spec:** `docs/superpowers/specs/2026-10-26-cart-sync-design.md`

## Global Constraints

- Branch `feat/cart-sync` (from `feat/auth`). Read `node_modules/next/dist/docs/01-app/` guides before Next.js code.
- `useCart()`'s return shape is unchanged; existing consumers (`CartView`, `ProductPurchase`, `Header`) are not edited for sync.
- The root layout does not change; `/`, `/cart`, `/products/[id]` stay static/ISR.
- Line validity: `id`, `size` non-empty strings; `quantity` integer 1–99. Max **50** lines. Same `id + size` → keep the **larger** quantity.
- Save debounce: **1000 ms** after the last change.
- localStorage keys: cart `storefront:cart:v1` (existing), owner `storefront:cart:owner` (new).
- Server Actions take the user id from `auth()` only; client-sent ids are never trusted.
- `public.carts`: RLS on, no policies, `revoke all ... from anon, authenticated`.
- Sync errors: `console.error` only, no UI.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Pull overwrites an unsaved change** — a focus pull while a save is pending must not replace the shopper's newer cart. Test in Task 4 (`hasPending()` true until a save succeeds, including after a failure).
2. **Save loop** — applying a server cart must not schedule a save. Test in Task 3 (`replaceCart` notifies with source `"remote"`, mutations with `"local"`).
3. **Someone else's leftover cart** — a browser owned by user A, signed in as user B, must `pull`, never `merge`. Test in Task 1.
4. **Garbage in localStorage or forged action payloads** — malformed lines must be dropped server-side. Test in Task 1 (`sanitizeCartLines`), enforced in Task 2.
5. **Sign-out inside the debounce window** — a change made <1 s before sign-out must still be saved. Test in Task 4 (`flush()` saves immediately), manual item 4 in Task 6.

### Task 4: Debounced saver

**Files:**
- Create: `lib/cart-saver.ts`, `lib/cart-saver.test.ts`

**Interfaces:**
- Consumes: `CartLine`
- Produces:
  - `export type CartSaver = { schedule(lines: CartLine[]): void; flush(): Promise<void>; hasPending(): boolean; cancel(): void }`
  - `export function createCartSaver(save: (lines: CartLine[]) => Promise<void>, delayMs = 1000): CartSaver`
  - Semantics: `schedule` keeps only the latest lines and restarts the timer; when it fires (or on `flush`) it calls `save` once; `hasPending()` is true from `schedule` until a `save` resolves for the latest lines; on rejection it `console.error`s and stays pending (the lines are kept for the next `flush`/`schedule`); `cancel` drops pending lines and the timer.

  - `flush saves immediately and clears pending`.
  - `flush with nothing pending does not call save`.
  - `stays pending after a failed save and retries on flush` — `save` rejects once then resolves; after the timer, `hasPending()` is true; `await flush()` → called twice, `hasPending()` false.
  - `cancel drops pending lines` — after `cancel()`, advancing time calls nothing and `hasPending()` is false.

### Task 5: CartSync wiring

**Files:**
- Create: `app/components/CartSync.tsx`
- Modify: `app/components/Header.tsx`, `app/components/SignOutButton.tsx`

**Interfaces:**
- Consumes: `decideSync`, `mergeCartLines` (Task 1); `loadAccountCart`, `saveAccountCart` (Task 2); `replaceCart`, `getCartLines`, `onCartChange`, `getCartOwner`, `setCartOwner` (Task 3); `createCartSaver` (Task 4); `useSession`
- Produces:
  - `CartSync` (`"use client"`, default export, renders `null`)
  - `export const cartSaver: CartSaver` and `export function flushCartSync(): Promise<void>` from `app/components/CartSync.tsx` — a module-level saver wrapping `saveAccountCart`, so `SignOutButton` can flush it

Behavior (effects call store functions, never React `setState`, so `react-hooks/set-state-in-effect` stays satisfied):
- On `status`/`userId` change and on `window` `focus`: compute `decideSync({ status, userId: session?.user?.id ?? null, owner: getCartOwner() })`.
  - `merge`: `loadAccountCart()`; on `null` or error stop (owner stays unset → retried later); else `merged = mergeCartLines(getCartLines(), account)`, `replaceCart(merged)`, `setCartOwner(userId)`, `cartSaver.schedule(merged)` then `flushCartSync()`.
  - `pull`: if `cartSaver.hasPending()`, call `flushCartSync()` instead (retries a failed save, per spec Error handling) and skip the load; else `loadAccountCart()` → if non-null `replaceCart(account)`, `setCartOwner(userId)`.
  - `clear`: `cartSaver.cancel()`, `replaceCart([])`, `setCartOwner(null)`.
- `onCartChange` subscription: when `source === "local"` and `getCartOwner()` equals the signed-in user id, `cartSaver.schedule(lines)`.
- Ignore a load result that resolves after the effect is cleaned up or the user changed (compare user id captured at start).
- `Header.tsx`: render `<CartSync />` next to `<AccountNav />` inside the existing `SessionProvider`.
- `SignOutButton.tsx`: `await flushCartSync()` (errors ignored) before `signOut({ redirectTo: "/" })`.
