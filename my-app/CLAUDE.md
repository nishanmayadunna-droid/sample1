# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Critical: this is not the Next.js in your training data

This project runs **Next.js 16.2.12** with **React 19.2**. APIs, conventions, and file structure may differ from what you remember. **Before writing any Next.js code, read the relevant guide under `node_modules/next/dist/docs/`** (the App Router docs live in `01-app/`) and heed any deprecation notices. Do not rely on remembered Next.js APIs.

## Commands

```bash
npm run dev     # start the dev server at http://localhost:3000
npm run build   # production build
npm run start   # serve the production build
npm run lint    # ESLint (flat config via eslint-config-next)
npm test        # Vitest (vitest run); single file: npx vitest run lib/auth-rules.test.ts
```

Vitest covers pure logic only (`lib/*.test.ts`); flows that touch Supabase or OAuth are checked manually in the browser.

## Architecture

This is a **demo storefront** (apparel) with cash-on-delivery orders. No online payments yet. Accounts use Auth.js (see below). The product catalog lives in Supabase (see below); the cart lives in the browser.

- **App Router** (`app/`). Root layout `app/layout.tsx` wires the fonts via `next/font/google` (Geist sans/mono + Anton display + Noto Sans Sinhala regular and bold-only → `--font-geist-*`, `--font-anton`, `--font-sinhala`, `--font-sinhala-bold`), sets the "Northbound" title template, renders the shell (see **Shell**), and imports `app/globals.css`. Routes: `/signin`, `/account`, `/admin` (see Auth), `/` (home — promotion banners, a compact hero only when no banner is running, the ⚡ Flash Deals row, the category shelf, the admin's promises, newsletter), `/products` (catalog; `?category=`, `?view=deals|picks|new` and `?q=` combine and show as removable chips), `/products/[id]` (detail; statically generated via `generateStaticParams`), `/cart`, `/checkout`, `/orders/[number]` (see Orders).
- **Product data** lives in the Supabase `public.products` table and is split across two modules. `lib/products.ts` holds the `Product` and `Category` types and pure helpers (`formatPrice`, `effectivePrice`, `discountPercent`); it's safe in client components. `lib/catalog.ts` is server-only and does the async reads (`getAllProducts`, `getProduct`, `getProductsByCategory`, `getCategories`, each wrapped in React `cache()`). It maps snake_case rows (`sale_price`, `material`/`construction`/`origin`, `image_url`) onto the camelCase `Product` shape. It uses a **cookie-less** supabase-js client on purpose, so catalog pages stay static/ISR (`export const revalidate = 60` on `/`, `/cart`, `/products/[id]`); don't switch it to `lib/supabase/server.ts`, which calls `cookies()` and would make every route dynamic. Client components never fetch products: server pages pass them down (e.g. `/cart` passes the full catalog to `CartView`, which computes the subtotal; the cart store holds only `{id, size, quantity}`). **Prices are stored in cents** (integers); render them through `formatPrice`, never with raw math. Sale items carry an optional `salePrice` — always charge/display `effectivePrice(product)` (falls back to `price`) and it's what the cart subtotal uses; `discountPercent()` drives the sale badges. Product photos are in the public Storage bucket `product-images` as `<product id>.jpg` (placeholder photos from picsum.photos, uploaded by `scripts/upload-product-images.mjs`). `app/components/ProductImage.tsx` renders them with `next/image` over a `swatch` gradient, which also serves as the fallback when `imageUrl` is null; pass `sizes` to match the slot and `preload` for above-the-fold images (`priority` is deprecated in Next 16). `next.config.ts` allows `<NEXT_PUBLIC_SUPABASE_URL>/storage/v1/object/public/**` in `images.remotePatterns`.
- **Sinhala / English** (pattern from the owner's POS): every customer-facing string is rendered in **both** languages with `<L si="…" en="…" />` (`app/components/L.tsx`, server-safe), and CSS on `html[data-lang]` hides the other one (`globals.css`; `.l-si` drops letter-spacing, which breaks Sinhala conjuncts). The choice is the `nb_lang` cookie, **never read by the server**: the root layout renders the admin's default language and an inline `<head>` script (`langBootScript` in `lib/i18n.ts`, rendered by `app/components/InlineScript.tsx` per the Next "preventing flash before hydration" guide) switches `data-lang` before first paint, so pages stay static. The rules (`resolveLang`, `tr`, the script) are pure and tested in `lib/i18n.ts`; a test runs the script against `resolveLang`, so change both together. Client components use `useLang()`/`setLang()` from `app/context/LangContext.ts` (a module store; `Header` calls `initLangStore(defaultLang)` first) and `tr(lang, si, en)` for attributes and alerts. Admin settings live in `public.store_settings` (one row: `default_lang`, `bilingual`), edited at `/admin/settings`; with `bilingual` off the `LangToggle` is hidden and the cookie ignored. Server actions return message **codes**, not text (sign-in/up: `lib/auth-messages.ts`). Admin pages, product/category data and `metadata` stay English. Sinhala copy needs the owner's review.
- **Shell** (root layout): `PromiseStrip` (black strip: the free-shipping line from `freeShippingThreshold(promotions)` — only while a running promotion offers shop-wide free shipping — then up to 3 admin promises; one at a time on phones), `Header` (logo, `SearchBox`, `LangToggle`, account, cart icon with badge; nav row ⚡ Flash Deals / ⭐ Top Picks / 🆕 New In / `CategoryMenu`), `CartDrawer` and `Footer`. The layout reads settings, products (as `ShellProduct`), categories, promises and running promotions in parallel with cookie-less clients (`lib/storefront.ts`, `lib/catalog.ts`), each falling back on its own, and has `revalidate = 60`; storefront admin writes call `revalidatePath("/", "layout")`. Search and `/products` share `matchesQuery`/`filterProducts` (`lib/product-filters.ts`). Cart money for the drawer and `/cart` comes from `summarizeCart(lines, products, promotions, shippingFee, categories)` (`lib/cart-summary.ts`), rendered by the shared `CartTotals`/`CartProgress`/`LinePrice` components. The drawer opens only through `openCartDrawer()` (`app/context/CartDrawerContext.ts`; the header button and add-to-cart), never on sync. Promises live in `public.store_promises` (`icon`, `text_si`, `text_en`, `sort_order`, `visible`; public SELECT of visible rows) and are managed at `/admin/promises` (`lib/admin-storefront.ts`, `app/admin/promises/actions.ts`; rules in `lib/storefront-form.ts`, at most 3 visible).
- **Promotions** (`lib/promotions.ts`, pure, tested): admin-made campaigns in `public.promotions` + `public.promotion_rules` (RLS: public SELECT of active ones only; writes via the secret key; rules replaced atomically by the `save_promotion_rules` SQL function, executable only by `service_role`). Rule kinds `free_shipping`, `percent_off`, `amount_off_item`, `amount_off_order`; scope all / category slugs / product ids; optional `min_subtotal` measured on list/sale prices **before** promotions. **Best price only**: an item costs the lowest of list price, `salePrice` and each matching item rule (nothing stacks); the single best qualifying order discount applies, capped at the subtotal; one qualifying item ships the whole order free; otherwise `store_settings.shipping_fee` (Rs 350, `/admin/settings`). There are **no shipping constants** — the old "free over Rs 5,000" is the seeded `free-shipping` promotion. `getRunningPromotions()` (`lib/storefront.ts`, cookie-less) decides what is running at render time; pages price products with `withPricing` → `PricedProduct` (`ProductCard` takes one), and the client (drawer, search, `/cart`) uses the same list, never its own clock, so they agree (ISR means ~1 minute lag at start/end). Banners: `PromoBanner` (template or uploaded image in the public `promotion-images` bucket, files `<slug>-<epoch>.<ext>`) and the `PromoBanners` slider on the home page; `/products?promo=<slug>` shows a promotion's products. Admin: `/admin/promotions` (`lib/admin-promotions.ts`, `app/admin/promotions/actions.ts`, validation in `lib/promotion-form.ts`; datetimes are Asia/Colombo, converted with `colomboToUtcIso`/`utcIsoToColombo`).
- **Product page** (`/products/[id]`): photos come from `public.product_images` (`product_id`, `path`, `sort_order` 0–4; RLS public SELECT, writes via the secret key), at most 5 per product (`MAX_PHOTOS`). `products.image_url` always equals the first photo, so cards, the drawer and search are unchanged; `lib/catalog.ts` embeds `product_images(path, sort_order)` in its select and `Product.gallery` is the ordered public URLs (rows → legacy `image_url` → none). Pure rules (`validatePhotoList`, `moveItem`, `parsePhotosField`, URL building) are in `lib/product-photos.ts`; the admin form sends the ordered storage paths as one JSON `photos` field and `setProductPhotos` (`lib/admin-products.ts`) replaces the rows, syncs `image_url` and best-effort deletes unused files. `ProductGallery` (client: thumbnails, arrow keys, swipe), `ProductPurchase` (size pills, chips, a phone-only sticky price + add bar that scrolls to the pills when no size is chosen) and `deliveryChips` (`lib/product-page.ts`: free shipping or the shop's `shipping_fee`, conditional offers, the promotion's end date) make up the page. **Migration state:** `20261103120000_create_product_images.sql` is run by the owner in the SQL editor and must be applied **before** the code that embeds the table is deployed.
- **Reviews and stock** (Part 4): `public.reviews` (`product_id`, `user_id`, `author_name` = first name only, `rating` 1–5, `body` ≤ 1000, `status` pending|approved|rejected, unique per `(product_id, user_id)`; RLS public SELECT of approved only, writes via the secret key) and `products.stock` jsonb (size → quantity; `null` or a missing size = not tracked, always available). **No checkout exists, so stock never decrements by itself** — the admin sets it per size in the product form and it isn't synced with the POS. Pure, tested rules: `lib/stock.ts` (`isSoldOut`, `allSoldOut`, `lowStockLeft` below 5, `maxQuantity`, `parseStockField`), `lib/reviews.ts` (`validateReview`, `summarizeRatings` → null with no reviews, `firstName`) and `clampToStock` in `lib/cart-rules.ts`. `lib/catalog.ts` embeds `stock` and approved `reviews(rating)` in the shared `selectProducts()` (so `Product.stock`/`rating` ride the ISR pages; hidden products expose neither) and `getProductReviews(id)` lists approved reviews. Customers review from the product page: `ReviewForm` (client, wrapped in its own `SessionProvider` because the page is outside the Header's) calls `submitReview` (`app/products/[id]/review-actions.ts`, `requireUser`, user id from the session, upserts the user's one review as `pending`; returns a message **code**). Admins moderate at `/admin/reviews` (`lib/admin-reviews.ts`, `app/admin/reviews/actions.ts`, each action starting with `requireAdmin`). Storefront: cards show ★ average (count) only when there are approved reviews; `ProductPurchase`/`QuickAdd` disable sold-out sizes, show "Only N left", and the add buttons stop at the cart cap; `CartStockGuard` (mounted in `Header`) clamps the cart with `setCartLines` and shows a notice when stock was cut. **Migration state:** `20261103180000_reviews_and_stock.sql` is run by the owner in the SQL editor and must be applied **before** the code that embeds it is deployed (the catalog select would otherwise fail for the whole shop).
- **Orders (COD)** (Part 5): `public.orders` (`order_number` NB-10001…, `user_id`, `idempotency_key` unique, `status` pending|confirmed|shipped|delivered|cancelled, `payment_method` 'cod', `payment_status` 'unpaid', delivery details, totals in cents) and `public.order_items` (snapshot of name, size, quantity, unit price; `product_id` set null if the product is deleted). RLS on, no client access; everything goes through the secret key in `lib/orders-data.ts` (`server-only`), and customer reads always filter by the session user id. **Stock is only changed inside two `service_role`-only SQL functions**: `place_order` (locks product rows in id order, refuses with `out_of_stock:<id>:<size>:<left>`, decrements tracked sizes, inserts order + items, returns the number; the same `idempotency_key` returns the same order) and `set_order_status` (enforces the transition table, stamps `*_at`, gives stock back on cancel). The transition table is duplicated in `lib/orders.ts` (`nextStatuses`) — change both together. **The browser never sets a price**: `/checkout` (dynamic, `requireUser`) shows a summary, but `placeOrder` (`app/checkout/actions.ts`) sends only cart lines + the total shown, and `planOrder` (`lib/order-plan.ts`, pure, tested) recomputes with `summarizeCart`, rejects unknown/hidden products, sizes not offered and over-stock quantities, and returns `price_changed` when the total differs. Pure rules (statuses, `normalizePhone` → `07XXXXXXXX`, `parseCheckoutDetails`, `orderTotals`) are in `lib/orders.ts`. Customers see `/orders/[number]` (404 for anyone else's) and the list on `/account`; they can cancel only while pending. Admins use `/admin/orders` (+ `[number]`), where `StatusButtons` offers only `nextStatuses`. A review gets `reviews.verified` when, at submit time, the author has a delivered order containing the product. `proxy.ts` also guards `/checkout` and `/orders`. **Later:** a payment gateway ("pay first, get a gift or discount") comes last. **Migration state:** `20261104100000_orders.sql` is run by the owner in the SQL editor and must be applied **before** the code that uses it is deployed (the review list selects `verified`).
- **Advance payments (Part 6)**: a customer who isn't **trusted** (`users.cod_trusted`) pays a small advance by bank transfer and uploads the slip; an approved slip makes them trusted (`cod_trusted_source` 'advance'), the admin can also trust/untrust by hand ('admin'), and trusted customers order with plain COD. Pure, tested rules in `lib/advance.ts`: `advanceFor(total, settings)` (modes `off` | `fixed` | `percent` with min/max, capped at the total), `advanceRequired(trusted, settings)`, `parseAdvanceSettings`, slip path rules (`slipPathFor`, `isValidSlipPath`, `MAX_SLIPS` 3, `SLIP_MAX_BYTES` 5 MB) and `paymentStatusLabel`. **Everything is private**: `payment_settings` (one row, default mode `off`, so applying the migration changes nothing until an admin turns it on), `bank_qr_codes` (≤ 4), `payment_slips`, and the private buckets `payment-qr` and `payment-slips` have RLS with no policies or grants; files are only ever shown through 60-second signed URLs made server-side per request, and uploads go browser → Storage with signed upload URLs (the path is checked and the file's existence verified before anything is recorded). `lib/payments-data.ts` (`server-only`) is the data layer. **Payment-state changes only happen in `service_role` SQL functions**: `place_order` takes `p_advance` (the order becomes `payment_method` 'cod_advance', `payment_status` 'advance_due'), `add_payment_slip` (owner + state + ≤ 3 slips → 'slip_uploaded'), `review_payment_slip` (locks the order first; approve → 'advance_paid' + customer trusted; reject → back to 'advance_due' when no other slip is pending) and `set_order_status` refuses to confirm an advance order until the advance is paid (`advance_unpaid`). **The browser never decides the advance or trusted state**: `placeOrder` computes both on the server and returns `advance_setup` (placing nothing) when an advance is required but the bank details are empty; the admin form also refuses to switch the advance on without them. Customer side: `/orders/[number]` shows `PaymentPanel` (bank details, QR images, slips, uploader; `app/orders/[number]/payment-actions.ts`) while the advance is due; `/account` shows "✓ Verified customer". Admin side: `/admin/payments` (mode, amounts with a live preview, bank details, QR images), `/admin/customers` (trust toggle) and the Payment section of `/admin/orders/[number]` (view slips, Approve / Reject with a reason; cancelling an advance-paid order warns to refund by hand). Not built: refunds, auto-cancel of orders whose advance never arrives, email/SMS. **Migration state:** `20261105100000_advance_payments.sql` is run by the owner in the SQL editor and must be applied **before** the code that uses it is deployed (checkout calls the new `place_order` signature).
- **Loyalty points (Part 7)**: customers earn points when an order is **delivered** and spend them at checkout as a discount on the goods. `public.points_settings` (one row, default **off**: `enabled`, `earn_per` cents of goods per point, `point_value` cents a point is worth, `max_percent` of the goods points may pay) and `public.points_ledger` (`kind` earn|redeem|refund|adjust, signed `points`, optional order and note) are private (RLS, no policies, no grants); **a balance is the sum of the user's ledger**. A partial unique index on `(order_id, kind)` for earn/redeem/refund makes each happen at most once per order. `orders` carry `points_used`, `points_discount` (cents) and `points_to_earn` (worked out by the server at placement with that moment's settings, so later settings changes never rewrite an order); `orders.total` already includes the points discount (`total = subtotal - discount - points_discount + shipping`, and `place_order` refuses a total that doesn't add up). **Points only move inside `service_role` SQL functions**: `place_order` (nine arguments: after the advisory lock and the pending cap it locks the user row, checks the ledger balance → `not_enough_points`, stores the order columns and inserts the `redeem` row), `set_order_status` (`delivered` inserts the `earn` row, any `cancelled` — including from shipped — inserts the `refund` row; both `on conflict do nothing`) and `adjust_points` (admin, refuses a negative balance). **The browser never decides points**: `CheckoutForm` only previews with the same pure `pointsToUse` (`lib/points.ts`, whole points, floor everywhere, capped by balance and `max_percent` of goods after promotions and before shipping), and `placeOrder` reads the balance and settings on the server and `planOrder` recomputes — a total that differs returns `price_changed`, `not_enough_points` returns `points_changed`; unreadable points settings count as off. The advance (Part 6) is computed on the final total. Customer side: points are only used when ticked; `/orders/[number]` shows points used, what will be earned, earned or returned; `/account` shows the balance, its value and the last 50 ledger entries (`lib/points-data.ts`, `server-only`). Admin side: `/admin/points` (switch, amounts, live example), a Points column and an adjust control (signed number + required note) on `/admin/customers`, and points lines on `/admin/orders/[number]`. Product pages and cards never mention points. Not built: bonus points, expiry, tiers. **Migration state:** `20261106100000_loyalty_points.sql` is run by the owner in the SQL editor and must be applied **before** the code that uses it is deployed (checkout calls the nine-argument `place_order`).
- **Order hygiene (Part 8)**: an advance order takes stock when placed, so `payment_settings.advance_expiry_hours` (default 48, **0 = never**, max 720) cancels it automatically if the advance doesn't arrive. `public.cancel_stale_advance_orders()` (`service_role` only) selects only **pending** orders with `payment_status = 'advance_due'` and `advance_amount > 0` — an order with a slip waiting for review (`slip_uploaded`) is **never** auto-cancelled, and a rejected slip restarts the clock (the clock is the later of `created_at` and the latest slip `reviewed_at`; the pure mirror is `advanceDeadline`/`isAdvanceStale` in `lib/advance.ts`). Each order is locked and re-checked, then cancelled through `set_order_status` (so stock and used points come back exactly as for a manual cancel) and stamped `orders.cancel_reason = 'advance_expired'`; a per-order exception block keeps one failure from stopping the rest, and two runs at once cancel an order once. It runs every 30 minutes through `pg_cron` (the **optional** migration `20261107110000_schedule_stale_cancel.sql`; the shop works without it) and by hand through the admin's **Cancel stale now** button (`/admin/orders?view=advance`, "Awaiting advance", which also shows each order's age, expiry and a "stale" mark). `public.waive_advance(order)` lets the admin drop the advance of a pending/confirmed order (for someone they now trust; the order page hints when the customer is trusted): `advance_amount` becomes 0, the order is plain `cod`/`unpaid` with the total unchanged (the customer pays all of it on delivery), pending slips become `waived`, and stock, points and trust are untouched. Customer side: the advance panel says "Please pay before <date>" (real data, only while no slip is under review and expiry is on), a system-cancelled order shows its reason, a waived order says the advance was waived. **Migration state:** `20261107100000_order_hygiene.sql` is run by the owner in the SQL editor and must be applied **before** the code that reads the new columns is deployed.
- **Phone sign-in (Part 9)**: next to email/Google, a customer can sign up and in with a Sri Lankan mobile number and a 6-digit SMS code (Text.lk). **Admin switch, default OFF**: `public.sms_settings` (one row: `enabled`, `sender_id`, `daily_cap` default 200, 1–5000), edited at `/admin/sms`; the page shows only whether the token is set, never its value. The token lives only in the server env var `TEXTLK_API_TOKEN` (`.env.local` and Vercel); the code hash key is `AUTH_SECRET`. `smsAvailable()` (`lib/sms-data.ts`) = enabled + sender id + token; with it false `/signin` shows no Phone tab and nothing is sent (an unreadable or missing table counts as off). **Accounts**: `users.phone` (unique, `07XXXXXXXX`), `users.email` is now **nullable** (check: password, Google id or phone), a phone account is never linked to an email/Google one, and display falls back to the phone number. **Codes** live in the private `public.phone_otps` (hash only, HMAC of `phone:code`, 5 min, one use, 5 wrong attempts); **all limits are in `service_role` SQL functions** under one advisory lock — `request_phone_code` (≥ 60 s apart, ≤ 5 per hour per phone, daily cap per Asia/Colombo day; a new code supersedes older ones), `verify_phone_code` (counts every wrong guess, never succeeds on the 6th), `cancel_phone_code`. `lib/phone-auth.ts` ties it together: `requestPhoneCode` (a failed send keeps its row, so it still counts toward the daily cap and the per-phone limits; the `cancel_phone_code` SQL function exists but is not used) and `verifyPhoneCode`, used by the Auth.js Credentials provider `phone` in `auth.ts`. Pure helpers (code, hash, recipient `94XXXXXXXXX`, settings parsing) are tested in `lib/otp.ts`; the HTTP call is `lib/sms.ts`. Every answer is the same whether or not the number has an account. Not built: password reset, linking a phone to an email account, changing a phone number, order SMS. **Migration state:** `20261108100000_phone_signin.sql` is run by the owner in the SQL editor and is additive (nothing reads it until the feature is switched on).
- **Product cards and the home page**: `ProductCard` (server) is an `<article>` — links on the photo and name only, never around the `QuickAdd` 🛒+ client island (one size → add + open the drawer; several → a size picker over the photo, one open at a time). Cards take a `PricedProduct` and show `pricing.price`, the struck list price and "Save Rs X"; `ProductGrid` lays them out 2 / 3 / 5 a row. Home selection rules are pure and tested in `lib/home-sections.ts` (`dealProducts`, `soonestDealEnd`, `shelfProducts`, `savedAmount`, `quickAddMode`). **No invented urgency**: `FlashCountdown({ endsAt })` only counts to a real running promotion's end (`soonestDealEnd`), starts from a placeholder so SSR and hydration match, and hides at zero. `CategoryShelf` is a client tablist over the priced products the page passes in. `ProductImage` takes `showCategory={false}` in small or badge-carrying slots.
- **Cart state** is in `app/context/CartContext.tsx`. Despite the name it is **not** React Context/a provider — it's a module-level store persisted to `localStorage`, exposed through the `useCart()` hook built on `useSyncExternalStore` (chosen so the React 19 `react-hooks/set-state-in-effect` lint rule stays satisfied, and for hydration + cross-tab safety). Consumers gate cart-dependent UI on the `hydrated` flag to avoid SSR/client mismatch. Mutations (`addItem`/`removeItem`/`setQuantity`/`clear`) are plain exported functions. **Signed-in carts sync to `public.carts`** (one row per user, `lines` jsonb; RLS on, no client access) through the render-less `app/components/CartSync.tsx`, mounted in the Header's `SessionProvider`. Pure rules live in `lib/cart-rules.ts` (`sanitizeCartLines`, `mergeCartLines`, `decideSync`): a guest cart (no owner) is **merged** on sign-in keeping the larger quantity per `id + size`; when the browser cart already has an owner it is **pulled** (replaced) on page load and window focus — never merged, so another user's leftover cart can't leak; signing out **clears** it. The owner is stored at `storefront:cart:owner`. Local edits are saved whole, debounced 1 s (`lib/cart-saver.ts`), via `app/cart/actions.ts` (`loadAccountCart`/`saveAccountCart`, user id from `auth()` only). `replaceCart` reports source `"remote"`, so applying a server cart never triggers a save. Local changes not yet confirmed by the server set a shared `storefront:cart:dirty` flag; while it's set, sync **pushes** the browser cart instead of pulling, so a reload, a quick tab switch or a failed save can't lose them. `proxy.ts` skips Server Action requests (`missing: next-action` header): the Auth.js `auth()` proxy wrapper re-sets the session cookie on every request it handles, so an action finishing after sign-out would sign the user back in. Matcher values must be inline literals (Next ignores variables). As a second guard, cart actions run through `lib/sync-gate.ts` and `SignOutButton` calls `prepareCartForSignOut()` first.
- **Server vs client**: pages/most components are Server Components. Only interactive pieces carry `"use client"` — `Header` (+ `AccountNav`, `CartSync`, `SearchBox`, `CategoryMenu`, `LangToggle`), `PromiseStrip`, `PromoBanners`, `CartDrawer`, `CartTotals`, `QuickAdd`, `CategoryShelf`, `PromotionClock`, `SignInForm`, `SignOutButton`, the admin forms (`ProductForm`, `PublishToggle`, `DeleteProduct`, `CategoryForm`, `DeleteCategory`, `LanguageForm`, `ShippingForm`, `PromiseForm`, `PromiseRowActions`, `PromotionForm`, `RulesEditor`, `DeletePromotion`), `ProductPurchase` (size selection + add-to-cart), `CartView`, `CheckoutForm`, `CancelOrderButton`, `PaymentPanel`, the admin payment forms (`PaymentSettingsForm`, `QrManager`, `TrustToggle`, `PaymentReview`, `PointsSettingsForm`, `AdjustPoints`, `CancelStaleButton`, `WaiveAdvanceButton`, `SmsSettingsForm`), `FlashCountdown`, `Newsletter` (client-side validation only; sends nothing), and the cart store.
- **Styling** is **Tailwind CSS v4** via PostCSS (`postcss.config.mjs` → `@tailwindcss/postcss`); no `tailwind.config.js`. All design tokens live in `app/globals.css`: raw CSS variables on `:root` (with a `prefers-color-scheme: dark` override) are mapped in `@theme inline` to the Tailwind color names `bg`, `surface`, `ink`, `muted`, `line`, `blaze` (the single orange accent), `panel`, `panelink`, `panelmuted` — use those (`bg-panel`, `text-blaze`, …), not default palette colors. The same file defines the brand's custom classes: `.display` (Anton, uppercase headings), `.eyebrow` (mono tracked-out spec label), `.measure` (ruler-tick rule), and `.rise` (hero load animation, disabled under reduced motion).
- **Supabase** (project `sample1`, ref `dtytkwxlpvkervhkhcpu`) is used for Database and Storage. Env vars `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (plus server-only `SUPABASE_SECRET_KEY`, used by scripts and `lib/supabase/admin.ts`) live in `.env.local` (git-ignored). Schema changes are recorded in `supabase/migrations/` with filenames matching the remote migration versions; there's no local Supabase CLI/stack, so migrations are applied to the remote project (via MCP `apply_migration`) and the same SQL is saved there. `products` is read-only to clients: RLS on, one public SELECT policy, no write grants. Edit catalog data through the admin pages (see below). Use `lib/supabase/server.ts` (`await createClient()`, per request) in Server Components/Actions/Route Handlers and `lib/supabase/client.ts` in client components. Only the publishable key may be `NEXT_PUBLIC_`; every table in `public` needs RLS.
- **Auth** is Auth.js v5 (`next-auth@5.0.0-beta.32`, pinned) configured in root `auth.ts`: Google + Credentials (email/password, bcryptjs cost 12), **JWT sessions, no adapter**. Accounts live in `public.users` (`role` is `'user'`|`'admin'`; RLS on, no policies, no client grants), reached only through `lib/users.ts` via the secret-key client `lib/supabase/admin.ts` (both `import "server-only"`). Not Supabase Auth — `lib/supabase/server.ts`/`client.ts` carry no user session. Pure decisions (sign-up validation, Google account-linking, `safeCallbackUrl`) live in `lib/auth-rules.ts` with unit tests. Accounts are never linked: an email belongs to either a password or a Google account, and the other method is rejected. The real access check is `requireUser()`/`requireAdmin()` in `lib/auth-guards.ts` (admin re-reads `role` from the DB; non-admins get `notFound()`); `proxy.ts` is only an optimistic redirect to `/signin`. **The root layout must not call `auth()`** (that would make every catalog page dynamic) — the Header reads the session client-side via `SessionProvider`/`useSession` in `AccountNav`. Sign-in/sign-out go through `next-auth/react` with a full navigation so that client session refreshes; `app/signin/actions.ts` only creates the account. Make someone admin by setting `role = 'admin'` in the dashboard. Env: `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET` (Google redirect URI `http://localhost:3000/api/auth/callback/google`). Session types are augmented in `types/next-auth.d.ts` (JWT under `@auth/core/jwt`). No password reset or email verification yet.
- **Admin products** (`/admin`, `/admin/products/new`, `/admin/products/[id]`): admins create and edit products, upload one photo each, hide/show them, and permanently delete them from the edit page's danger zone (type the id to confirm; `deleteProduct` removes the row, then best-effort its photo). `products.published` (default true) hides a product — `lib/catalog.ts`'s shared `selectProducts()` filters `published = true`, so hidden products leave every shop list and their pages 404. Validation (and price dollars → integer cents, photo path rules) is pure and tested in `lib/product-form.ts`. Server code is `lib/admin-products.ts` (secret-key client, includes hidden products) and `app/admin/products/actions.ts`, where **every action starts with `await requireAdmin(...)`** because Server Actions are endpoints of their own. Photos go browser → Storage directly: `requestImageUpload` issues a signed upload URL for `<id>-<epoch ms>.<ext>` (JPEG/PNG/WebP, ≤ 5 MB) and the form calls `uploadToSignedUrl`; on save the path is checked (`isValidImagePath`, exists) before anything is written, `image_url` is updated and the old file is best-effort deleted. New names per upload keep CDN/`next/image` caches from serving an old photo. Every write calls `revalidatePath` for `/`, `/products`, `/products/<id>`, `/cart` and `/admin`.
- **Categories** live in `public.categories` (`slug` primary key — immutable, used in URLs like `/products?category=outerwear` — plus editable `name`, a two-colour `swatch` for the home tile, and `sort_order`; public SELECT, writes via the secret key). Admins manage them at `/admin/categories` (`lib/admin-categories.ts`, `app/admin/categories/actions.ts`, each action starting with `requireAdmin`); a category with products can't be deleted. Pure rules are in `lib/category-form.ts`. **Migration state:** both steps are applied. Step 2 (`supabase/migrations/20261102200211_link_products_to_categories.sql`) lowercased `products.category` to slugs and added the `on delete restrict` foreign key; it was run in the SQL editor, so it isn't in the remote migration history. It is one-way: don't roll production back past the categories code. `resolveCategoryParam` still accepts a name or a slug, so old `?category=Outerwear` links keep working. Products carry `categoryName` for display.
- **TypeScript** path alias `@/*` maps to the project root (e.g. `@/lib/products`).
- **Agent skills** are vendored twice — `.claude/skills/` and `.agents/skills/` (tracked by `skills-lock.json`) — and are not part of the app. `AGENTS.md` carries the same "read the bundled Next.js docs first" rule as above.
